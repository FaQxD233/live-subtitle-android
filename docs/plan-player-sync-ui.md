# 计划：B 站拖动后字幕提前、控制栏整理和其他改进

状态：待确认（2026-11-27 起草，同日修订多次，见第 9 节）

## 1. 目标与范围

**目标**

1. B 站拖动进度条后，字幕比画面快 1–2 秒，直到下一次暂停才纠正。改成拖动后字幕先等一等再走，等多久按 B 站自己前几次报出的差值来定（第 3 节）。单纯的暂停、继续，记录里没有累积，不改。
2. 整理字幕播放的控制栏：信息分层，调试入口和少用的按钮收起来。
3. 其他改进：README 跟上跟随功能，长提示不再被截掉，对齐值按字幕记住，通知使用权改成控制栏里的说明。

**验收标准**

- B 站拖动攒够 2 个样本之后，再拖动时字幕不再明显提前：剩余误差多数在 0.3 秒以内（现在是 1.1–1.9 秒）。B 站哪次加载得特别慢时会超出，下一次暂停照旧纠正。
- 单纯暂停、继续时不触发等待（诊断里没有等待记录，单测也覆盖）。
- 控制栏宽度不随内容伸缩，窄屏上不超出屏幕；胶囊文字在中英文和系统大字体下不截断；信息行内容变了控制栏高度不变；所有提示都能完整显示。
- 调过对齐的字幕，关掉再打开时自动套用上次的对齐，一键能归零。

**不做**

- 不读通知：通知栏里的进度就是 B 站会话上报的那份数据，App 已经在直接读（第 2 节）。
- 不用声音信号（原方案 A，已撤掉，见第 3.4 节）。
- 不识别画面，不做语音对齐。
- 不改实时翻译的链路（只缩短它一条过长的提示）。
- 主界面这轮不动（见第 5 节第 4 项）。

## 2. B 站读数记录说明了什么

**通知栏里的进度从哪来**

- 媒体通知本身不带播放位置，只带一个会话令牌和几个按钮：`Notification.MediaStyle` 和播放有关的只有 `setMediaSession`、`setShowActionsInCompactView`、`setRemotePlaybackInfo`。来源：[Notification.MediaStyle](https://developer.android.com/reference/android/app/Notification.MediaStyle)。
- 系统的媒体控件从会话读元数据，进度条对应会话的 `PlaybackState`；没设时长，进度条就不显示进度。来源：[媒体控件](https://developer.android.com/media/implement/surfaces/mobile)。
- AOSP 的 SystemUI 按「报的位置 + 速度 ×（现在 − 上报时刻）」算当前进度，播放时每 100 ms 重算一次。它用的是手里缓存的那份上报，不会向 App 要新数据；时长为 0 或更小时进度条不可用。来源：[SeekBarViewModel.kt](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/src/com/android/systemui/media/controls/ui/viewmodel/SeekBarViewModel.kt)（`computePosition`、`POSITION_UPDATE_INTERVAL_MILLIS`）。
- 所以通知栏显示的进度和 `VideoTime.positionAt` 算出来的是同一个数：公式一样，数据也是同一个会话的同一份上报。读通知不会更准。

**2026-11-27 外放的记录**（Xiaomi 2407FRK8EC，Android 14，约 171 秒，状态行「跟随 bilibili」）

| 项 | 记录 |
|---|---|
| 什么时候报 | 只在暂停、继续、拖动时报，共 14 次；正常播放中一次都不报 |
| 报告晚到 | 每份上报的时间戳都比送到时早 203–230 ms（平均 216 ms）；YouTube 是 2–11 ms |
| 继续时的位置 | 5 次继续，报的位置都和刚才暂停时一样（精确到 0.1 秒） |
| 单纯暂停、继续 | 2 次，下一次暂停报的位置离按「继续」那份上报外推的只差 +18 ms、−6 ms |
| 拖动 | 3 次，都在播放中。B 站松手就报「在新位置播放」，下一次暂停报的位置比按那份上报外推的少 1942、1147、1073 ms |
| 开头 | 记录开始时 B 站已在播放，第一次暂停的 drift −669 ms |
| 最后 | 暂停在 1:49.7（读数精确到 0.1 秒）；B 站进度条显示 1:50，字幕的时间显示 1:49 |

**2026-11-27 戴蓝牙耳机的记录**（约 73 秒）

| 项 | 记录 |
|---|---|
| 报告晚到 | 205–224 ms（平均 214 ms），和外放时一样 |
| 单纯暂停、继续 | 6 次，drift +5、−8、−98、−23、−52、+6 ms（平均 −28 ms） |
| 拖动 | 1 次（往前约 11 秒），下一次暂停的 drift −1067 ms |
| 开头 | 记录开始时 B 站已在播放，第一次暂停的 drift −943 ms |

**推断**

- **暂停、继续没有累积，戴蓝牙耳机也一样。** 跟随时每份上报都会把字幕拨到 B 站报的位置。单纯暂停、继续之后，B 站下一次报的位置和字幕外放时只差 0.02 秒以内，戴耳机时差 0.1 秒以内。如果 B 站继续时没算上蓝牙那段延迟、报早了，戴耳机时每次暂停的 drift 都会在 −0.1 到 −0.3 秒。
- **拖动后字幕快 1–2 秒。** B 站拖动后马上报「已经在新位置播放」，其实视频还要 1–2 秒才真正走到那里：要么在加载，要么是从前面一点开始播的。记录分不出是哪种，但两种情况下字幕该做的一样：停在新位置，等这么久再走。B 站之后一直不报，字幕就一直快，直到下一次暂停。两份记录共 4 次拖动，晚到 1.94、1.15、1.07、1.07 秒，除了 1.94 那次都很接近。
- **刚开始播放时也偏早。** 两份记录开头第一次暂停都差了 0.7–0.9 秒，看起来 B 站开始播放时报的那份也是加载完之前的，和拖动是同一回事。还不确定这两次是怎么开始播放的（在 B 站里打开视频，还是在控制栏点的播放），见第 5 节第 7 项。
- **报告晚到 0.2 秒**：暂停时，字幕会多走约 0.2 秒再退回 B 站报的位置；继续时，字幕晚约 0.2 秒才动，然后跳到位。都不累积；B 站晚报的这 0.2 秒，我们没法提前知道。
- **最后那 1 秒**：字幕停在 1:49.7，时间显示把小数舍掉（`DateUtils.formatElapsedTime(ms / 1000)`），显示成 1:49。这次是外放，暂停时画面没有多走，画面也停在 1:49.7 左右；B 站显示 1:50，说明它是四舍五入。这 1 秒完全是两边显示取整不同。
- **之前看到的「刹车」是蓝牙耳机的延迟**（2026-11-27 你确认：前一天戴蓝牙耳机时暂停有延迟，这次外放没有）。暂停后，已经送到耳机的那段声音还会响一小会儿，不是 B 站的视频多走了。戴耳机的记录也对得上：B 站报的位置照样准。

## 3. 方案 A：拖动后先等一等再走

### 3.1 规则

- **什么算拖动**：跟随的视频在播放中来了一份上报，位置离上一份外推的位置差 3 秒以上（和诊断里的 `JUMP_MS` 同一个门槛）。用回调里 B 站原样的上报判断，带它自己的时间戳。
- **怎么等**：字幕停在拖到的位置，到「B 站的时间戳 + 等待时长」再开始走。等的时候 B 站来了新上报（比如你又暂停了，或者它报了缓冲），照常处理，不再等。
- **等多久**：这个 App 最近 5 个样本的中位数（偶数个时取偏小的那个）；攒够 2 个才开始等，最多等 3 秒。中位数不会被偶尔一次特别快（比如命中缓存）或特别慢的拖动带偏。
- **样本怎么取**：只认拖动后的下一份上报，而且要同时满足：
  - 它是「暂停」（缓冲、又一次拖动、别的状态都不算）；
  - 它在拖动后 3 秒到 2 分钟之间到来：太早，视频可能还没加载完；太晚，中途可能卡过，会被算成拖动的；
  - 中间标题没变（有元数据的 App 换集、换视频时不算）。
- **样本的单位**：drift 是视频时间，等待是现实时间，所以样本 = −drift ÷ 拖动时的倍速，小于 0 记 0。2× 下加载 1 秒，drift 是 −2 秒，样本是 1 秒。
- **存**：每个 App 记最近 5 个样本，存在设置里（和 `seekableApps` 一样），下次打开还能用，每个 App 只需攒一次。
- **只管播放中拖动**。暂停时拖动再继续、刚打开新视频，这次记录里没有，先不管。B 站没有元数据，换集时认不出来，会当成一次拖动：多等约 1 秒，和开播的加载时间相近，影响小。
- **按时间顺序算两份记录**（样本跨次保存）：第 1、2 次还没攒够样本，照旧提前 1.94、1.15 秒；第 3、4 次都等 1.15 秒，慢 0.08 秒；再往后等 1.07 秒。像这样的拖动剩余误差在 0.1 秒以内；1.94 那种特别慢的一次会提前约 0.8 秒。

### 3.2 放在哪、怎么测

- 认拖动、取舍样本、算等待放在纯 Kotlin 的 `DragWait` 里，`VideoFollower` 只把每份原样的上报交给它。连续拖动、等待中暂停、缓冲、倍速、换标题、太早太晚，都在 CI 的单测里覆盖（第 7 节）。

### 3.3 诊断多记两样

- 读数里每个 App 多一行：学到的等待时长和最近的样本。
- 每次拖动记一行：等了多久。拖动后的下一份上报再记一行：这次样本多少、记没记，不记时写原因（太早、太晚、不是暂停、标题变了）。

### 3.4 报告晚到、时间显示

- 报告晚到 0.2 秒造成的那两下小跳不改：B 站晚报，我们没法提前知道。
- 时间显示照旧舍掉小数；要和 B 站对时间，看诊断里精确到 0.1 秒的位置。

### 3.5 手动模式、蓝牙耳机，和撤掉的声音方案

- 手动模式这轮不改：记录说明 B 站能跟随。
- 蓝牙耳机不用改。戴耳机的记录里每次暂停的 drift 都接近 0（第 2 节），B 站继续时没有报早，不用给「继续」学等待；暂停时多听到的那一点，是耳机里还没放完的声音。字幕和耳机里的声音是不是同时，只能靠听：字幕总是早一点的话，对齐一次就好。
- 声音事件已撤掉。拖动后 B 站什么都不报，系统的「播放器开始出声」事件是唯一能精确知道视频什么时候真正走起来的旁证；但只在 B 站加载时会停声才有用，而且要按时间去对是哪个 App 的声音。先用 3.1 的办法；剩下的误差还嫌大，再考虑在诊断里只记录、不改行为地看看它靠不靠得住。

## 4. 方案 B：控制栏整理

### 4.1 现在的问题

- 第一行挤着时间、临时提示、调试用的「会话」按钮，以及锁定、收起、关闭。
- 「跟随」按钮和右边的状态是挨着的两个控件：开没开只看按钮底色，状态文字能点，但看不出能点。
- 字号 A− / A+ 和播放控制挤在同一行。
- 图标混用：上一句、下一句、播放、关闭用的是系统自带的老图标，各品牌手机上长得不一样，和锁定、收起这些自绘图标也不是一个风格。
- 卡片宽度随内容变化。
- 跟随时 ±0.5、上一句 / 下一句改的是对齐，但界面上看不到现在对齐了多少，也没法一下回到 0。
- 长提示用的是 Toast，而 Android 12 起 Toast 最多显示两行（目标 API 31 及以上，本项目是 34）。锁定提示、首次使用提示、通知使用权说明的后半截都被截掉了。来源：[Android 12 行为变更](https://developer.android.com/about/versions/12/behavior-changes-12)。

### 4.2 新布局

```

│ 01:23 / 45:00  字幕推后 0.5 秒  会话 锁 — ✕ │

└───────────────────────────────────────────┘

之后（宽 300dp；屏幕更窄时缩到屏幕宽减两边边距）

│ ━━━━━━━━━━━━━━●───────────────────  1×   │  进度条占满，右边是倍速
│ 1:23:45                       2:45:00    │  时间在进度条两端下方

├╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┤

└──────────────────────────────────────────┘
```

- **状态胶囊**代替「跟随」按钮和状态行，只放短状态：「跟随 bilibili」「等视频」「广告中」「换了视频」「没报位置」「需要权限」「手动」，放不下时末尾省略。圆点绿色表示正在跟随，黄色表示在等，灰色表示手动；有两个以上会话才显示 ⇄。需要多说的放进信息行，比如「bilibili 换了视频，点胶囊接着跟」。
- **点胶囊**做当下最需要的事：没权限就展开说明面板（第 5 节第 2 项）；换了视频就接着跟；有多个会话就切换 App；手动就打开跟随；正在跟随且只有一个会话时展开 ⋮ 行，关跟随的开关在那里。
- **宽度**：300dp；屏幕更窄时（分屏、小窗、折叠屏外屏）缩到屏幕宽减两边边距。
- **进度行**：进度条占满一行，右边是倍速；时间放在进度条两端下方，一小时以上的视频也不挤。
- **信息行**一直占一行高度，内容变了控制栏也不跳。跟随时显示当前对齐（如「字幕提前 1.37 秒」，0 时显示「未调对齐」），不为 0 时右边有「归零」；手动时显示一句操作提示。按 ±0.5 等之后短暂显示这次调了多少。同时有几样要显示时，顺序是：刚调的对齐 > 状态说明 > 当前对齐。
- **说明面板**：需要多行说明时在信息行下面展开，带按钮。用在通知使用权说明（去开启 / 取消）和第一次使用的用法（知道了）。
- **⋮ 展开的一行**：「跟随视频」开关、A− / A+、「诊断」（就是原来的「会话」读数，长按复制）。
- 图标统一换成自绘的矢量图标（上一句、下一句、播放、暂停、关闭）。小胶囊在跟随时多一个绿点。

### 4.3 提示

- 锁定提示缩到 20 字左右，比如「已锁定：触摸穿透，双击暂停字幕，点胶囊解锁」；跟随时去掉双击那句。Android 12 起 Toast 左边还带应用图标，要留足余量。
- 首次使用的用法改放在说明面板里。
- 通知使用权说明也改放在说明面板里，见第 5 节第 2 项。
- 实时翻译悬浮窗的点击穿透提示，英文版超过两行，一起缩短。

## 5. 其他改进

**建议这轮一起做**

1. **README 跟上**：功能列表、权限表补上通知使用权；「字幕播放」一节按新控制栏和跟随重写；删掉已知限制里「字幕播放靠手动对齐」这条过时的说明；项目结构补上新文件。
2. **通知使用权说明**（原计划阶段 3）：点胶囊时在控制栏的说明面板里说明为什么要、不读通知内容；Android 13 起附上受限设置的步骤。点「去开启」才跳设置页，和现在一样从悬浮窗拉起（阶段 0 时在你手机上就是这样打开的）。不另开 Activity：普通 Activity 的窗口在悬浮窗下面，会被控制栏和字幕盖住。
3. **对齐值按字幕记住**（原计划阶段 2）：关闭播放器或换文件时，和位置一起存进 `SubtitlePositions`；再打开同一个字幕时自动套用，信息行提示「已套用上次的对齐」，旁边就是「归零」。实时翻译录下的字幕记录偏移量通常很大，最需要这个。

**以后再说**

4. **主界面**：给字幕播放单独一块（打开文件、字幕记录、跟随状态），现在只有两个文字按钮。
5. **只跟对齐过的那个 App**：现在视频暂停时，微信语音或音乐 App 一开始播放，字幕就会跟着它们的进度跳，等视频继续才切回来。可以改成别的 App 只在胶囊上提示，点一下才切过去。
6. B 站修好、数据确认后，删掉诊断读数（原计划阶段 3）。
7. **刚开始播放时也等一等**：YouTube 从头播放时字幕偶尔早约 0.9 秒（阶段 0 里两次早约 0.9 秒、一次晚约 0.4 秒）；B 站两份记录开头那次也早 0.7–0.9 秒。都是开始播放时报的那份在加载完之前，到下一次暂停才纠正。可以按 3.1 同样的办法单独学一个「开始」的等待，但要先弄清开始播放时 App 怎么上报（是不是新会话，我们能不能收到它原样的第一份上报），才知道怎么认出「开始」。

## 8. 风险与需要你决定的事

**风险**

- 等待时长是按前几次估的：某次拖动 B 站加载得特别快，字幕会晚一点，到下一次暂停纠正。用中位数，偶尔一次特别快或特别慢不会带偏之后的等待。
- 冷启动慢：要攒 2 个样本，拖动后 3 秒到 2 分钟内暂停一次才算一个。样本跨次保存，每个 App 只需攒一次。
- 开头那段的临时误差（第 5 节第 7 项）可能让你顺手调了对齐，又被记住带到下次：信息行一直显示当前对齐，可以一键归零；开播的等待做了以后，这个问题会小很多。
- 两份记录共 4 次拖动，3 次在 1.07–1.15 秒，1 次 1.94 秒；次数还少，诊断会继续记下来。
- 不能本地编译，全靠 CI；XML 布局、矢量图标和字符串最容易因笔误挂掉，所以分两批验证。
